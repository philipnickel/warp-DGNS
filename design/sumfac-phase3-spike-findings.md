# Phase 3 Spike Findings — Codegen Dispatch Feasibility

**Date:** 2026-06-09 · **Spec risk:** §9.1 (highest) · **Verdict:** use the existing machinery

**Recommendation:** `existing-machinery`

## Prototype agreement vs naive integrate()

YES — exact agreement to float64 roundoff on both required devices. Fused single-kernel B^T D B vs naive fem.integrate() for the 2D mass form u*v, Grid2D 4x2 (8 elements, bounds (1.0, 1.5)), discontinuous P=3 space (128 DOFs), RegularQuadrature order 6 (4x4 GL): cpu: max |sumfac - naive| = 1.735e-17 absolute, 6.456e-16 relative; cuda:0: max |sumfac - naive| = 2.082e-17 absolute, 7.748e-16 relative (result magnitudes ~2.7e-2; np.testing.assert_allclose(rtol=1e-12, atol=1e-13) passes on both). The kernel exercised the full target pipeline: tile_matmul B-stage interpolation, then per-QP in-kernel invocation of the IntegrandTransformer-transformed user integrand d+1 = 3 times (SeedField value seed + 2 physical gradient seeds, trial value injected via a ValueInjectedField EvalArg member written in-kernel from the B-stage tile), then B^T tile_matmul contraction of f0 AND the (identically zero) f1x/f1y gradient channels including the J^{-1} reference mapping, with tile_store scatter. Re-run confirmed all generated modules load from cache (kernel suffix caching idempotent). No fallback architecture was needed — no wall was hit; struct construction in-kernel (FieldStruct()/EvalArg()), nested member assignment on local structs, tile element extract (uq[qx,qy]) and assign (f0[qx,qy] = ...) between tile ops, and repeated transformed-integrand calls all compiled and ran correctly first try on both devices (first CUDA module compile 37.8 s due to mathdx LTO; cached afterwards).

## Rationale

The existing machinery handles every hard part of the staged kernel with zero changes, proven by a working end-to-end prototype: (1) cache.get_integrand_kernel + PassFieldArgsToIntegrand are agnostic to kernel-body contents — the code transformer (integrate.py:498-619) only rewrites integrand_func call-site arguments by AST name, so a kernel_fn full of wp.tile_load/tile_matmul/tile_reshape/tile_store compiled and cached through it unchanged; there is in-tree precedent, since get_integrate_constant_kernel (integrate.py:625-678) already mixes per-thread integrand_func calls with wp.tile_sum/wp.tile_atomic_add and is launched with an explicit block_dim (integrate.py:1342-1360). (2) IntegrandTransformer needs no modification: operator resolution is purely field-type-driven (integrate.py:265-306 dispatches inner/grad to field.eval_inner/eval_grad_inner), so substituting SeedField (already in field/virtual.py:409) for the test field and a ValueInjectedField for the trial input reuses the user's integrand body verbatim as the in-kernel Q-function — exactly the mechanism qfunction.py already uses host-side, now proven to work between tile ops inside one wp.launch_tiled kernel on cpu and cuda:0. (3) Launch metadata is not part of the generated kernel: _launch_integrate_kernel already branches per kernel flavor with bespoke dims/block_dim/temporaries (constant: lines 1342-1360; LocalTestField: 1444-1494), so a sumfac branch using wp.launch_tiled plus a staging temporary is structurally idiomatic, not a parallel system. (4) Caching: kernel_suffix tuples accept the extra (E_b, n, q, dim) discriminators and the spike verified clean cache hits on re-run. What does NOT fit is only glue, not architecture: the field substitution must happen before _gen_field_struct/IntegrandTransformer.apply (a ~10-line restructure inside _generate_integrate_kernel), the suffix must be recomputed after substitution, and the launch branch needs extra array inputs (1D operators, staging) — all the same kind of per-variant code the nodal/local/constant flavors already add. 'parallel-generator' is therefore unjustified, and 'hybrid' overstates it: the sumfac kernel factory in sumfac/kernels.py is a sibling of get_integrate_linear_kernel, generated, transformed, cached, and launched by the existing pipeline.

## Proposed Phase 3 shape

SUFFICIENT EVIDENCE THAT NO PARALLEL GENERATOR IS NEEDED; sumfac/kernels.py mirrors the existing get_integrate_*_kernel factory pattern.

warp/_src/fem/sumfac/kernels.py:
- `def get_integrate_linear_sumfac_kernel(integrand_func: wp.Function, domain: GeometryDomain, quadrature: Quadrature, FieldStruct: Struct, ValueStruct: Struct, test: TestField, input_field: ValueInjectedField, *, n: int, q: int, dim: int, element_batch: int, accumulate_dtype) -> Callable` — returns a kernel_fn closure exactly like get_integrate_linear_kernel (integrate.py:681); body = B stage (tile_load packed DOFs -> tile_matmul against 1D I/D̂, per tensor_contract.py canonical patterns), D stage (per-QP loop: quadrature.point_coords/weight + domain.element_measure + element_deformation_gradient; fresh local FieldStruct with EvalArg.value injected from B tile; d+1 SampleType rebuilds with DofIndex(0,0)/DofIndex(1+i,0) seeds; integrand_func(sample, qp_fields, values); J^{-1} maps physical f1 seeds to reference), B^T stage (transposed tile_matmuls, tile_store per-element residual). n/q/E_b products baked as wp.constant.
- `class ValueInjectedField(AdjointField)` — promote the spike's trial-value injection field into field/virtual.py next to SeedField (EvalArg carries `value` (+ `gradient` later); eval_inner returns args.eval_arg.value; fill_eval_arg is a no-op). This is the sibling already sketched in sumfac/qfunction.py's "Trial-value injection (Phase 3)" docstring.
- `def make_sumfac_field_args(arguments: IntegrandArguments, test, input_field) -> IntegrandArguments` — SeedField/ValueInjectedField substitution (mirrors qfunction.py:279-283).
- `def sumfac_applicable(integrand, arguments, test, trial, quadrature, domain) -> bool` — must check ALL of: (1) domain.element_kind == ElementKind.CELL and domain.geometry.cell_dimension == dimension (tensor-product quad/hex geometry); (2) test is a plain TestField (NOT LocalTestField, NOT nodal i.e. quadrature is not None), trial is None for the Phase 3 apply path; (3) test space is discontinuous tensor-product (square/cube shape function) with NODE_DOF_COUNT == VALUE_DOF_COUNT == 1 (SeedField scalar-only) and degree >= low-P threshold; (4) quadrature is a RegularQuadrature whose points match the operators_1d.default_quadrature_points tensor order (verified host-side, as in the spike's ordering assert); (5) integrand.operators on the test field ⊆ _SUPPORTED_TEST_OPERATORS (reuse the frozenset from qfunction.py:100) and on the input field ⊆ {inner, outer, degree} (add grad/grad_outer once gradient injection lands); (6) FEM_SUMFAC config flag (auto|force|off).

Dispatch hook in _generate_integrate_kernel (integrate.py:1110): the hook must land BEFORE FieldStruct/IntegrandTransformer construction (lines 1140-1148), not just before the kernel_fn if-chain, because the SeedField/ValueInjectedField substitution changes the field_args that _gen_field_struct and IntegrandTransformer.apply consume. Concretely: after _notify_operator_usage (line 1123), `if _sumfac_enabled() and sumfac_applicable(...): arguments = make_sumfac_field_args(arguments, test, ...)` and select integrate_kernel_fn = get_integrate_linear_sumfac_kernel(...) in the `trial is None` branch; everything downstream (cache.get_integrand_kernel + PassFieldArgsToIntegrand at lines 1226-1238) is reused verbatim, except PassFieldArgsToIntegrand is constructed with fields_var_name set to the kernel's local per-QP struct name (its existing constructor kwarg, integrate.py:505).

Cache key design: kernel_suffix = ("sumfac", element_batch, n, q, dim, quadrature.name, field_names_AFTER_substitution, pod_type_key(output_dtype), pod_type_key(accumulate_dtype)). E_b/n/q/dim are mandatory in the suffix because they are baked into the closure as wp.constant tile shapes; field names must be recomputed post-substitution (see new_risks). Tuples of ints/strings work as-is with cache._make_key (verified: spike suffix ("sumfac-spike", quad.name, field_names, 4, 4, 2, 1) cached and was a clean hit on re-run).

Launch side: add a sumfac case to the linear-form branch of _launch_integrate_kernel (next to the LocalTestField case at integrate.py:1444), doing: (a) fetch/cache device arrays for the 1D I/D̂ operators (host-cached per (space basis, quadrature, device), like RegularQuadrature.CachedFormula); (b) borrow a (element_count, n^dim) staging temporary; (c) wp.launch_tiled(kernel, dim=[element_count // E_b], block_dim=_default_block_dim(device)); (d) scatter staging to the partition node vector with a small dynamic kernel using space.topology.element_node_index (or tile_store directly into the output when the DG node layout is element-contiguous). Per-element DOF gather for the input field should move in-kernel in the real implementation (pass the DiscreteField dof array as an extra kernel arg and gather via topology in the B stage) — the spike used host packing via topology.element_node_indices() only for brevity.

## Newly discovered risks (not in the design doc)

- Redundant per-lane D-stage execution: under wp.launch_tiled there is no lane index (wp.tid() returns the block index only), so every lane in the block (64 on CUDA) redundantly executes the per-QP scalar integrand evaluations and writes the same value into tile elements. Correct (verified on cuda:0) but a (d+1)*block_dim-fold redundancy in the D stage; perf risk at heavy Q-functions. The alternative two-index launch pattern (wp.launch(dim=(blocks, lanes), block_dim=lanes) as in get_integrate_constant_kernel, integrate.py:647) exposes a lane index, but tile element writes from divergent lanes are unverified and would need their own spike before use.
- Uniform-control-flow constraint: no early returns are allowed in the staged kernel body because all lanes must reach every tile op (the constant kernel at integrate.py:650-661 shows the required NULL-element fallback pattern). Partial panels (element_count % E_b != 0) must be handled by padding/clamping, not by returning early.
- Kernel cache-key collision hazard: kernel_suffix at integrate.py:1126-1127 is computed from the ORIGINAL field names, but the sumfac path substitutes SeedField/ValueInjectedField (changing field types, FieldStruct, and the transformed integrand). cache.get_integrand_kernel keys only on (integrand.func, suffix, options), so the sumfac branch must recompute field_names after substitution AND add an explicit marker + (E_b, n, q, dim) to the suffix, or naive and sumfac kernels can silently collide.
- Kernel-parameter structs are effectively immutable: the injected trial value cannot be written into the 'fields' kernel argument; the kernel must build a fresh local FieldStruct() and fresh EvalArg() per QP and copy the other members (this pattern compiles and runs on both devices; it constrains the kernel-factory code shape and is not mentioned in the design).
- Scalar-only restriction propagates to dispatch: SeedField raises for NODE_DOF_COUNT != 1 (virtual.py:447), so sumfac_applicable must also reject vector/tensor-valued spaces; the design's qualification list (spec 5/9.3) mentions only operators/domain/order, not value DOF count.
- mathdx LTO compile latency multiplies across kernel shapes: the single (4,4) fp64 shape set in this spike took 37.8 s on first CUDA module load. Phase 3 tests at P=1..8 x 2D/3D each bake distinct (n,q,E_b) wp.constants into the closure, i.e. distinct LTO compiles; the CI/test-runtime budget needs explicit shape reuse (the design discusses runtime perf but not JIT cost of the shape matrix).
- E_b>1 interaction with the D stage: the wide first contraction makes per-element slices of the stage-1 tile strided views; scalar tile_extract from strided views is fine, but the per-element f0/f1 must be fresh contiguous tiles before the backward tile_matmul (known strided-operand gotcha, but it dictates the D-stage loop structure: seeds must write into contiguous per-element tiles, adding ~ (1+d) q^d * E_b doubles of shared memory per block).
